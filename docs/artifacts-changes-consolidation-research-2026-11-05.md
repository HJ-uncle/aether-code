**“把文件改动变成成果”应当如何定义**

在当前产品里，适合采用的对象关系是：一个会话中的一个文件，对应一个成果树条目；这个条目关联多次修改记录、当前可读取内容，以及尚待确认的修改范围。

以围棋项目为例，README 被编辑十次，用户仍只需找到一个 README。需要追问「这轮为什么改了测试数字」时，再查看对应轮次或单次修改。整个项目可以继续由文件树表达，无须先把每个工具调用包装为成果卡片，也无须先建设新的成果存储系统。

成果入口中的“存在”不等于“已经验收”。至少要分清三类信息：

- 当前文件情况：存在、已删除、无法读取、已被后续编辑等。
- 修改审阅情况：待确认、已保留、已撤回。
- 内容来源与范围：当前文件、历史操作快照、预览片段等。

一个已经撤回的修改可以保留在历史里，但不能因此显示为仍可使用的交付文件。创建后又删除的临时文件也是同样道理。若未来增加“主要交付物”分类，可以降低临时文件的展示优先级，但不能隐藏其仍需处理的修改记录。

当前名为 WorkArtifact 的旧模型从聊天工具与命令回执派生，每次写入都有 ID，并不等同于现有成果树模型：[work-state.ts:334](D:/dev/aether-code/src/renderer/src/contrib/work/work-state.ts:334)。因此“合并界面入口”不应演变成把持久账本退回聊天消息解析。

**最重要的语义边界：现在的合并改动不是会话最终差异**

现有成果请求 `status=pending&view=net`。引擎也明确只支持 pending 净变化：[changes.ts:17](D:/dev/ai-agent-engine/src/api/http/routes/changes.ts:17)。

例如，一个文件从 A 修改成 B，用户保留后，又从 B 修改成 C。此时待确认差异是 B → C；它不能冒充整个会话的 A → C。全部保留之后，文件仍在成果树中，但默认视图会退回最新一次操作，而不是自动得到 A → C。

该回退是当前明确的行为：[work-session-artifacts.ts:204](D:/dev/aether-code/src/renderer/src/contrib/work/work-session-artifacts.ts:204)，测试也专门覆盖它：[work-session-artifacts.spec.ts:148](D:/dev/aether-code/e2e/work-session-artifacts.spec.ts:148)。同路径有多个净变化段时，树上的默认增删数也只是当前选中或默认段的统计，不能称为整个文件的会话累计修改量。

因此建议保留现有能力，同时把范围解释写清，例如「待确认改动」或「合并改动 · 仅待确认」。若以后增加“整个任务最终差异”，必须单独定义任务基线、已保留记录、外部手动编辑和不连续版本链的处理规则，不能在前端直接拼接第一次 oldContent 与最后一次 newContent。

当前实现正确保留了这些边界：

- 单轮净变化只有在所有源 changeIds 都属于该轮时才纳入，不能仅凭最后一次修改的 turnId 推断。
- 同一路径上不连续的版本链必须分段，不能合并成虚构快照。
- 引擎会省略安全可确认的零净变化段，但原始操作仍有历史意义。
- 文件的“当前内容”可能包含后续人工修改，必须和“本会话修改”区别展示。

依据：[work-session-artifacts.ts:94](D:/dev/aether-code/src/renderer/src/contrib/work/work-session-artifacts.ts:94)、[changes/index.ts:253](D:/dev/ai-agent-engine/src/storage/changes/index.ts:253)。

**建议的导航和详情结构**

保留「成果」作为统一入口，延续现在的文件树、搜索和会话/轮次选择。单个文件详情逐步形成以下三种查看方式：

| 视图 | 回答的问题 | 适合的动作 |
|---|---|---|
| 当前内容 | 这个文件现在是什么样，能否使用？ | 文档预览、运行 HTML、复制、保存、引用 |
| 待确认改动 | 当前还有哪些修改需要我处理？ | 看净变化、保留、撤回 |
| 修改记录 | 某一轮、某一次操作具体做了什么？ | 看历史差异、定位具体记录、显式撤回允许撤回的记录 |

不必把全部操作永久堆在工具栏上。文件有待确认改动时突出审阅动作；历史记录按需展开。代码任务可以继续默认打开现有差异视图，避免改掉用户已经喜欢的使用方式。

默认视图还应尊重来源：

| 入口 | 目标 |
|---|---|
| 聊天中「查看全部成果」 | 整个会话，清除旧搜索与轮次限制 |
| 查看某轮产生的文件 | 明确指定该轮，不能用时间近似归属 |
| 工具卡片上的某一次修改 | 指定会话、文件、changeId，进入对应修改记录 |
| 文档链接或打开文件 | 查看当前内容 |
| 资源文件内「查看改动」 | 同一会话、完整路径下的待确认改动或历史 |
| 冲突报告中的文件 | 定位到对应文件和失败记录 |

当前聊天摘要本身按整个 session 汇总。只改标题时适合叫「成果」或「会话成果」；不能未经范围改造就叫“本轮成果”。

当前预览能力可复用 [WorkArtifactPanel.tsx:110](D:/dev/aether-code/src/renderer/src/contrib/work/WorkArtifactPanel.tsx:110)。它优先读取真实文件，历史回执兜底有来源提示，也已有复制、保存、引用、文档预览与 HTML 运行能力。

**为什么仍然要保留改动能力**

保留与撤回作用于实际文件，不能因改了导航就弱化其契约：

- 保留确认已经发生的写入，不会重新写文件，不等于 Git 暂存、提交或发布。
- 批量操作只处理当前指定范围的 pending 记录；历史 kept 记录的撤回是单项显式操作。
- 撤回要核对当前版本，冲突或缺少可用快照时保持文件，并逐项报告。
- 任务继续运行、切换会话、切换引擎、确认期间记录发生变化时，旧确认不能继续生效。
- 文件审阅的撤回保留对话；从消息发起的轮次回退有自己的范围和截断对话规则。

上述能力已集中于 [WorkChangeReviewActions.tsx:55](D:/dev/aether-code/src/renderer/src/contrib/work/WorkChangeReviewActions.tsx:55) 与 [work-change-review.ts:7](D:/dev/aether-code/src/renderer/src/contrib/work/work-change-review.ts:7)。不需要新造另一套“成果确认”接口。

Git 页仍然有独立价值：它回答整个仓库相对 Git 基线发生了什么，也包含其他会话或手动编辑，并提供暂存、提交等功能。Code 模式的 ChangesPanel 还包含“暂存并保留”，不能因删除 Work 的旧标签一起移除。

**落地顺序与完成条件**

第一步：合并重复入口，保留现有成果体验。

1. 聊天「查看全部」转到成果，并明确清除旧搜索与轮次筛选。单次点击继续保留准确 changeId。
2. 移除 Work「改动」顶部标签与更多菜单项；持久化的旧 `changes` 布局映射到 `files`。
3. 资源文件的改动子页改为共享成果详情，或提供「在成果中查看改动」，避免继续保留独立查询/操作页面。
4. 更新冲突提示、空状态、测试入口等文案，避免留下不可达的“改动面板”。
5. 保持当前文件树与差异为主的体验，不强制切换为预览或卡片流。

第二步：补齐同一文件的当前内容与历史。

1. 复用当前预览组件，在文件详情中切换当前内容、待确认改动与修改记录。
2. 更清楚地区分存在、删除、撤回、已保留、读取失败等状态；全部保留之后仍然能找到文件与历史。
3. 统一会话文件记录的读取与状态订阅，减少摘要、成果、资源子页各自查询造成的不一致。界面合并本身不会自动消除全部重复请求。
4. 若有明确需求，再设计任务最终差异或主要交付物分组。它们不是删除重复标签的前置条件。

第一步实施前必须处理一个覆盖差异：旧页由 `workProgressChanges` 合并工具回执与 HTTP 记录，成果只接受归属明确的持久账本记录。命令、子 agent、旧历史的回执在同步间隙可能先出现在摘要里。成果应显示“正在同步此修改”并重试；确实没有记录时如实提示，不应按文件名或模型输出文本虚构成果，也不应放松会话归属验证。

导航实现可以扩展现有 WorkArtifactSelection，表达“整个会话 / 指定轮次 / 指定文件 / 指定操作”的意图。只将 `openWorkspace('changes')` 字符串替换成 `files` 不足以保证正确，因为成果可能还保留着上一次搜索和轮次范围。

| 场景 | 应满足的结果 |
|---|---|
| 旧入口导流 | 顶部与更多菜单只有成果；旧布局可恢复；查看全部清除筛选 |
